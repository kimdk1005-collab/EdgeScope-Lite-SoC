## p.3 — The Challenge `⏱ 1:00–2:05`

**화면 큐** — ① 상단 CPU→CH0→…→CH7 화살표를 왼쪽에서 오른쪽으로 훑고 ② `MISSED PULSE!` 지점에서 멈춥니다 ③ 하단 세 박스를 하나씩 짚습니다.

**대본**

> 문제 정의부터 말씀드리겠습니다.
>
> FPGA나 임베디드 보드에서 내부 신호를 볼 때 가장 흔한 방법은, CPU가 GPIO를 반복해서 읽는 **폴링**입니다. 위 그림처럼 CPU가 CH0부터 CH7까지 차례로 읽어 나가는데, 문제는 CH4를 읽고 CH5를 읽는 그 사이에 짧은 펄스가 들어오면, 그 펄스는 시스템 입장에서 **아예 존재하지 않았던 사건**이 된다는 점입니다.
>
> 한계를 세 가지로 정리했습니다.
>
> 첫째, **관측 주기가 흔들립니다.** CPU 부하와 인터럽트에 따라 폴링 간격이 달라지기 때문에, 일정한 샘플 타이밍을 보장할 수 없습니다.
>
> 둘째, **짧은 신호를 놓칩니다.** 폴링과 폴링 사이에 발생한 펄스는 기록되지 않고, 여러 채널에서 동시에 일어난 이벤트의 선후 관계도 신뢰할 수 없게 됩니다.
>
> 셋째, **사건 이전의 이력이 없습니다.** 문제가 터진 것을 확인한 다음에야 데이터를 모으기 시작하니까, 정작 원인 분석에 필요한 pre-trigger 데이터가 남지 않습니다.
>
> 이건 추측이 아니라 저희가 같은 보드에서 실제로 측정한 결과입니다. CPU 폴링 방식으로는 10 나노초와 100 나노초 펄스를 **열 번 시도해서 한 번도** 잡지 못했고, 1 마이크로초 이상이 되어야 안정적으로 검출됐습니다.

**메모** — 마지막 실측 문장이 이 슬라이드의 힘입니다. 여기서 청중이 "그래서 하드웨어가 필요하겠구나"를 받아들이면 나머지 발표가 쉬워집니다.

## p.4 — Project Goals `⏱ 2:05–3:00`

**화면 큐** — 오른쪽 세 카드를 위에서부터 하나씩. `1,024 / 512:512` 큰 숫자에서 한 박자 쉽니다.

**대본**

> 그래서 목표를 세 가지로 잡았습니다.
>
> 첫째, **병렬 캡처**입니다. 8개 채널을 서로 다른 시점이 아니라 **동일한 클럭 에지에서 한꺼번에** 샘플링하고, 채널당 최대 100 MS/s를 지원합니다.
>
> 둘째, **결정적 트리거**입니다. Rising, Falling, Masked Pattern 조건을 소프트웨어가 아니라 **하드웨어가 판정**하고, 이벤트당 정확히 한 번의 트리거 펄스를 만듭니다.
>
> 셋째, **독립적인 읽기**입니다. 트리거 직전 512개와, 트리거 샘플을 포함한 이후 512개, 합쳐서 1,024개를 시간 순서대로 보존합니다. MicroBlaze는 캡처가 끝난 뒤에 이걸 읽어서 UART로 내보냅니다.
>
> 이 세 목표를 관통하는 설계 원칙은 **역할 분리**입니다. 실시간 샘플링과 트리거 판정은 FPGA 하드웨어가 전담하고, MicroBlaze는 설정과 데이터 전송만 담당합니다. 그래서 CPU가 아무리 바빠도, UART가 아무리 느려도, 캡처 품질은 영향을 받지 않습니다.

**메모** — "역할 분리"는 뒤의 p.13, p.14, p.20에서 계속 되돌아오는 문장입니다. 여기서 한 번 명확하게 심어 둡니다.

## p.7 — System Specification `⏱ 4:00–5:05`

**화면 큐** — 왼쪽 표 → 가운데 위 IMPLEMENTATION METRICS → 가운데 아래 TIMING CLOSURE → 오른쪽 FINAL ACCEPTANCE.

**대본**

> 목표 사양과 최종 인수 기준입니다.
>
> 왼쪽이 설계 목표입니다. 8채널 디지털 입력, 100 MHz 시스템 클럭, 최대 샘플레이트 100 MS/s, 캡처 깊이 1,024, Pre/Post 512 대 512, 캡처 메모리 4 KiB, 트리거는 Rising·Falling·Masked Pattern 세 가지입니다.
>
> 가운데는 실제 구현 결과입니다. 여기서 중요한 건 **B 마이너스 A**라는 표기입니다. A는 CPU 폴링 기준군, B는 EdgeScope-Lite, C는 Vivado ILA인데, 셋 다 같은 Base SoC 위에 올려서 **베이스 SoC 비용을 뺀 순수 애널라이저 비용**으로 비교했습니다. 그 기준으로 저희 애널라이저가 추가로 쓴 자원은 Slice LUT 423개, Register 486개, BRAM 타일 1개, DSP는 0개입니다.
>
> 가운데 아래는 타이밍입니다. 100 MHz 제약에서 WNS 플러스 0.832 나노초, TNS 0으로 클로저를 만족했습니다.
>
> 오른쪽이 최종 인수 기준 네 가지입니다. 100 MHz 타이밍 클로저, 트리거가 논리 인덱스 512에 정확히 오는 캡처 정확도, ILA 대비 낮은 LUT·FF 사용량, 그리고 연속 3회 시연 성공입니다. 네 항목 모두 충족했고, 그 근거를 지금부터 순서대로 보여드리겠습니다.

**메모** — "B−A" 개념을 여기서 확실히 못 박아야 p.17·p.18의 절감률 이야기가 통합니다. 이 슬라이드에서 30초를 써도 아깝지 않습니다.

## p.8 — System Configuration `⏱ 5:05–6:10`

**화면 큐** — 왼쪽 SYSTEM INTEGRATION 블록도 상단(캡처 흐름) → 하단(제어·읽기 흐름) → 오른쪽 KEY CONFIG → CLOCK/RESET/IRQ.

**대본**

> 시스템 구성입니다. 보드는 Basys3, FPGA는 XC7A35T, CPU는 RISC-V 기반 소프트코어인 MicroBlaze V, 버스는 AXI4-Lite, 로컬 메모리 128 KiB, 캡처 메모리는 1,024 워드 곱하기 32비트, UART는 9600 보드레이트입니다.
>
> 왼쪽 그림이 이 프로젝트의 구조를 한 장으로 보여줍니다. **위쪽이 데이터가 흐르는 캡처 경로**입니다. probe 8비트가 Probe Sampler로 들어가고, 샘플 데이터와 valid 신호가 Trigger Engine과 Circular Trace Buffer로 **동시에** 갑니다. 트리거가 걸리면 Trace Buffer가 BRAM의 Port A로 계속 씁니다. 여기까지는 전부 하드웨어이고 CPU는 개입하지 않습니다.
>
> **아래쪽이 제어와 읽기 경로**입니다. MicroBlaze가 AXI Interconnect를 통해 IP별 레지스터를 설정하고, 캡처가 끝난 다음 AXI BRAM Controller로 Port B에서 읽어서 UART로 내보냅니다. 그림 아래에 적힌 대로 **하드웨어가 캡처하고 소프트웨어가 읽어 간다**는 게 핵심입니다.
>
> 오른쪽 아래는 주소 맵입니다. Sampler가 0x4001_0000, Trigger가 0x4002_0000, Trace Buffer가 0x4003_0000이고, 캡처 BRAM이 0x4200_0000입니다. IP마다 독립된 base address를 쓰기 때문에 세 IP를 따로 개발하고 나중에 합칠 수 있었습니다.

**메모** — ⚠️ 슬라이드의 `GPIO 0x4001_0000`은 오기입니다. 실제 Block Design에서 AXI GPIO는 **0x4000_0000**이고 0x4001_0000은 Sampler입니다(`comparison/common/base_soc.tcl:322`). 발표에서는 GPIO 주소를 굳이 읽지 마시고, 가능하면 슬라이드를 고쳐 두세요.

## p.9 — Custom IP Architecture `⏱ 6:10–7:00`

**화면 큐** — 01 → 화살표 라벨(`sample_data_o[7:0] + sample_valid_o`) → 02 → 화살표 라벨(`trigger_pulse_o`) → 03 → 아래쪽 파란 선(Same Sample Stream) → 하단 CSR/BRAM 바.

**대본**

> 지금부터 저희가 직접 RTL로 설계한 Custom IP 3종입니다. 세 IP가 파이프라인처럼 이어집니다.
>
> **Probe Sampler**가 8채널을 병렬로 샘플링해서 `sample_data`와 `sample_valid`를 만듭니다. 이 스트림이 **Trigger Engine과 Trace Buffer에 동시에 fan-out**됩니다. 이 부분이 중요한데, 트리거를 판정하는 회로와 데이터를 저장하는 회로가 **똑같은 샘플**을 보고 있기 때문에, 트리거가 걸린 그 샘플과 저장된 그 샘플이 어긋날 수가 없습니다.
>
> **Trigger Engine**은 그 스트림에서 조건이 맞는 순간 1클럭짜리 `trigger_pulse`를 냅니다.
>
> **Circular Trace Buffer**는 평소에 계속 링버퍼로 덮어쓰다가, 트리거 펄스를 받으면 512개를 더 채우고 멈춥니다. 그래서 트리거 이전 512개와 이후 512개가 남습니다.
>
> 아래 바에 적힌 대로 세 IP 모두 **각자의 AXI4-Lite 레지스터**를 갖고 **공통 100 MHz 클럭** 하나로 동작합니다. 오른쪽 Capture BRAM은 True Dual-Port로, Port A는 하드웨어 쓰기 전용, Port B는 CPU 읽기 전용입니다.

## p.10 — Probe Sampler IP `⏱ 7:00–8:05`

**화면 큐** — 왼쪽 Core Role 4줄 → 오른쪽 Architecture 블록 4개 → Sample Rate Table → Register Map.

**대본**

> 첫 번째 IP, Probe Sampler입니다.
>
> 역할은 8개 디지털 채널을 병렬로 샘플링하는 것입니다. 100 MHz 시스템 클럭에서 동작하고, 1·2·4·8 분주를 지원하며, 샘플이 유효한 순간마다 **1클럭짜리 `sample_valid` 펄스**를 만듭니다.
>
> 내부 구조는 오른쪽처럼 네 단계입니다. Clock Enable Divide, Sampler & Mask, Sample Valid Generator, Sample Counter입니다.
>
> 여기서 설계상 가장 중요한 판단이 첫 번째 블록입니다. 분주할 때 **새로운 클럭을 만들지 않고 Clock Enable 방식**을 썼습니다. 그림 아래 문구 그대로입니다. 분주 클럭을 따로 만들면 클럭 도메인이 늘어나서 CDC 문제와 타이밍 클로저 부담이 생깁니다. 그래서 클럭은 100 MHz 하나만 두고, enable 신호로 샘플링 주기를 조절했습니다. 이 결정 덕분에 시스템 전체가 **단일 클럭 도메인**으로 유지됐고, 뒤에 나올 타이밍 클로저도 여유 있게 통과했습니다.
>
> 아래 표대로 divider_sel이 00이면 100 MS/s, 01이면 50, 10이면 25, 11이면 12.5 MS/s입니다. 레지스터는 CONTROL, CONFIG, LAST_SAMPLE, SAMPLE_COUNT 네 개입니다.

**메모** — "왜 clock enable인가"가 이 슬라이드의 유일한 심사 포인트입니다. 나머지는 빠르게 넘어가도 됩니다.

## p.11 — Basic Trigger Engine IP `⏱ 8:05–9:20`

**화면 큐** — Core Role 4줄 → Architecture 5블록 → 아래 Trigger Mode Table → Register Map.

**대본**

> 두 번째 IP, Basic Trigger Engine입니다. 8비트 샘플 스트림을 보면서 트리거 이벤트를 찾아내는 회로입니다.
>
> 구조는 다섯 단계입니다. Sample History Register가 직전 샘플을 기억하고, Edge & Pattern Detect가 현재 샘플과 비교해서 조건을 판정하고, Mode Select Mux가 어떤 모드인지 고르고, ARM/TRIGGER FSM이 상태를 관리하고, 마지막에 32비트 Trigger Counter가 누적 횟수를 셉니다.
>
> 모드는 네 가지입니다. 00은 Disabled, 01은 Rising — 지정한 채널이 0에서 1로 갈 때, 10은 Falling — 1에서 0으로 갈 때, 11은 Pattern — **샘플과 마스크를 AND한 값이 기대값과 마스크를 AND한 값과 같을 때**입니다. Pattern 모드가 있기 때문에 "CH0과 CH3이 동시에 1이고 나머지는 무시" 같은 조건도 걸 수 있습니다.
>
> 동작 방식은 **원샷**입니다. ARM을 걸고, 조건이 검출되면 래치되고, CLEAR를 써야 다시 무장됩니다. 한 번의 캡처에 트리거가 여러 번 걸려서 데이터가 뒤섞이는 일을 막기 위한 설계입니다.
>
> 그리고 그림 아래 한 줄이 중요합니다. **트리거 펄스는 조합 논리로, 조건이 맞는 바로 그 사이클에 나옵니다.** 레지스터를 한 단 더 태워서 다음 클럭에 내보내면 트리거 샘플과 저장 위치가 한 칸 어긋나게 됩니다. 그래서 같은 사이클에 내보내도록 설계했고, 이 정렬이 맞는지는 뒤에서 파형으로 검증한 결과를 보여드리겠습니다.

**메모** — ⚠️ 슬라이드 부제의 `maked-patten trigger dectector`는 `masked-pattern trigger detector` 오타입니다. 화면에 크게 나오니 가능하면 수정하세요.

## p.12 — Circular Trace Buffer IP `⏱ 9:20–10:50`

**화면 큐** — 왼쪽 FSM을 IDLE부터 아래로 한 단계씩 손으로 내려갑니다 → 오른쪽 위 BRAM 그림 → 오른쪽 CAPTURE TIMING 막대 → 하단 레지스터 6개.

**대본**

> 세 번째 IP, Circular Trace Buffer입니다. 이 프로젝트에서 가장 핵심적인 IP이고, "트리거 이전 데이터가 없다"는 처음의 문제를 실제로 해결하는 부분입니다.
>
> 왼쪽 FSM을 따라가겠습니다.
>
> IDLE에서 ARM을 받으면 **PREFILL**로 갑니다. 여기서 링버퍼를 계속 돌면서 덮어씁니다. 유효 샘플 512개가 채워지면 — 즉 pre-trigger 분량이 확보되면 — **ARMED** 상태가 되고, 이때부터 트리거를 받을 준비가 끝난 겁니다.
>
> 트리거가 들어오면 **POST_CAPTURE**로 넘어갑니다. 여기서 트리거 샘플 자신을 첫 번째로 세어서 총 512개를 더 저장하고, 다 채우면 **DONE**과 함께 인터럽트를 올립니다.
>
> 결과가 오른쪽 CAPTURE TIMING 막대입니다. 총 1,024개 중 앞의 512개가 트리거 이전, 인덱스 512가 트리거 샘플, 그 뒤 511개가 트리거 이후입니다. 즉 **트리거의 논리 인덱스는 항상 512로 고정**됩니다. 어떤 조건으로 캡처하든 파형의 정중앙이 사건 발생 시점이라는 뜻이라서, 분석할 때 매번 트리거 위치를 찾을 필요가 없습니다.
>
> 오른쪽 위는 메모리 구조입니다. True Dual-Port BRAM을 써서 Port A는 Trace Buffer Core가 쓰기 전용으로, Port B는 AXI BRAM Controller를 통해 MicroBlaze가 읽기 전용으로 씁니다. 그리고 **읽기는 DONE 이후에만** 허용합니다. 캡처 중에 CPU가 끼어들어서 성능이나 데이터 무결성이 흔들리는 상황을 아예 구조적으로 차단한 겁니다.
>
> 아래 레지스터에서 실용적으로 중요한 건 세 개입니다. START_ADDR는 가장 오래된 샘플의 물리 주소, TRIGGER_ADDR는 트리거 샘플의 물리 주소, WRITE_ADDR는 마지막으로 쓴 주소입니다. 링버퍼라서 물리 주소 순서와 시간 순서가 다른데, 소프트웨어가 START_ADDR부터 읽어 나가면 **시간순으로 재정렬된 1,024개**를 얻게 됩니다.

**메모** — 90초를 배정한 이유가 마지막 문단입니다. "물리 순서 ≠ 논리 순서, START_ADDR가 그 변환의 열쇠"까지 말해야 wrap-around 검증(p.16)이 왜 필요했는지가 이해됩니다.

**대본**

> 앞의 세 IP를 실제 SoC에 통합한 모습입니다.
>
> 왼쪽이 프로세서 서브시스템입니다. MicroBlaze V 소프트코어가 100 MHz로 동작하고, 128 KiB 로컬 메모리를 쓰며 캐시는 없습니다. MDM 디버그, AXI INTC, 그리고 Clocking Wizard의 MMCM이 100 MHz 하나를 공급합니다.

**메모** — "아래쪽 경로에 CPU가 없다"가 p.4에서 심은 역할 분리의 회수 지점입니다. 손으로 아래쪽 점선 박스 전체를 한 번 훑으면서 말하면 효과적입니다.

**화면 큐** — 왼쪽 TEST STAGE 3단계 → 오른쪽 FIRMWARE CONTROL FLOW 01→08 순서 → 그 아래 진행 순서 바 → 오른쪽 아래 TEST PROGRAM EVIDENCE.

**메모** — ⚠️ 슬라이드 오타: `frimware`→`firmware`, `Tigger ARM`→`Trigger ARM`, `Triiger`→`Trigger`, `PREPIII`→`PREFILL`. 시간이 밀리면 이 슬라이드는 "여덟 단계이고, 6번 다음에 7번이라는 순서가 핵심입니다"로 35초에 끝낼 수 있습니다.

>
> 오른쪽 아래가 세 트리거 모드별 결과입니다. Rising은 선택 채널의 0→1 전이 샘플이 512에 정렬됐고, Falling은 1→0 경계가 512에서 확인됐고, Pattern은 샘플과 마스크를 AND한 값이 일치하는 샘플이 512에 표시됐습니다. **세 모드 모두 같은 읽기 경로로 검증**했습니다.

**대본**

> 베이스라인을 뺀 순수 애널라이저 비용 기준입니다.

>
> 마지막으로 **트레이드오프**도 정확히 말씀드리겠습니다. 저희는 전용 캡처 BRAM을 쓰기 때문에 ILA보다 BRAM 타일을 0.5개 더 씁니다. 대신 얻은 것이 Vivado 없이 UART와 CSV만으로 결과를 볼 수 있는 독립성입니다.

# 부록 A. 예상 질문과 답변

**Q. 왜 Vivado ILA를 안 쓰고 직접 만들었나요?**
> ILA는 훌륭한 기준 도구지만 JTAG 케이블과 Vivado 하드웨어 매니저가 항상 붙어 있어야 합니다. 저희는 보드 단독으로 캡처하고 UART로 결과를 뽑는 걸 목표로 했습니다. 그리고 결과적으로 애널라이저 순수 자원 기준으로 ILA보다 79.5% 적은 슬라이스로 같은 100 MS/s를 냈습니다.

**Q. B가 A보다 자원을 더 쓰는데 왜 "효율적"이라고 하나요?**
> A는 전용 캡처 하드웨어가 아예 없는 소프트웨어 기준군이라 기능이 동등하지 않습니다. 그래서 A는 절감률의 비교 대상이 아니라 **공통 SoC 비용을 빼기 위한 베이스라인**으로만 씁니다. 절감률은 같은 하드웨어 캡처 방식인 B와 C 사이에서만 이야기합니다.

**Q. 100 MS/s인데 UART가 9600 bps면 병목 아닌가요?**
> 캡처와 전송이 분리되어 있어서 병목이 되지 않습니다. 캡처는 BRAM에 100 MHz로 끝내고, UART는 캡처가 완료된 **DONE 이후에** 1,024개를 읽어서 내보냅니다. 전송 속도는 결과를 보는 데 걸리는 시간에만 영향을 주고, 캡처 품질에는 영향을 주지 않습니다.

**Q. 트리거가 안 걸리면 시스템이 멈추나요?**
> 아닙니다. 펌웨어에 타임아웃이 있고, 타임아웃이 나면 ABORT로 FSM을 IDLE로 되돌립니다. 이 복구 경로도 회귀 테스트 항목에 포함되어 있습니다.

**Q. 왜 pre/post를 512 대 512로 정했나요?**
> BRAM 1,024 워드를 반으로 나눈 값이고, 트리거를 항상 파형 정중앙에 두면 분석 도구에서 트리거 위치를 매번 계산할 필요가 없기 때문입니다. 다만 이건 상수라서 파라미터화하면 비대칭 분할도 가능합니다.

**Q. 캡처 깊이를 늘리려면 무엇이 필요한가요?**
> BRAM 타일과 주소 폭입니다. XC7A35T에서 현재 50개 중 33개를 쓰고 있으니 여유가 있고, Trace Buffer의 depth 파라미터와 AXI BRAM Controller의 range를 함께 늘리면 됩니다.

**Q. 여러 클럭 도메인의 신호도 볼 수 있나요?**
> 현재 설계는 단일 100 MHz 도메인 전용입니다. 다른 도메인 신호를 보려면 입력단에 동기화기를 넣어야 하고, 그 경우 동기화 지연만큼의 시간 불확실성을 감안해야 합니다. 확장 과제로 두고 있습니다.

**Q. 전력 4.9% 감소는 실측인가요?**
> 아닙니다. post-route 벡터리스 추정값이고 신뢰도는 Medium입니다. 슬라이드에도 각주로 명시했습니다.
